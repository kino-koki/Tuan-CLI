# 模块一 · 系统与基础设施（8 项目）

**模块定位**：当你面对系统软件、基础设施、数据库、高并发组件、CLI 工具时使用。这一层的项目动辄存活 20 年以上，它们的竞争力几乎全部来自"模型选择 + 契约稳定"，而非功能堆叠。本模块蒸馏 Linux、Git、nginx、Redis、SQLite、PostgreSQL、curl、FFmpeg 的共同规律。

## 核心法则

1. **接口契约是系统软件的命根子。** Linux 的 syscall 与 POSIX 接口几十年来保持兼容，应用生态才能在其上生长；PostgreSQL 的 SQL 方言是其三十年不衰的底座。做系统级组件时，把"对外契约"当作永久承诺来设计，给它写文档、加版本、走变更流程。
2. **模型对了，性能是免费的；模型错了，调参是徒劳的。** nginx 用事件驱动替代进程/线程模型，让万级并发成为默认能力；Redis 在内存里存结构化数据，让复杂操作保持微秒级；PostgreSQL 的 MVCC 让读写不互斥。选型时先问"用什么模型"，再问"怎么优化"。
3. **复杂度的敌人是状态共享。** Redis 用单线程 + 事件循环消灭了并发状态；SQLite 用单写者 + 文件锁消灭了多进程状态；Git 用内容寻址 + 不可变对象消灭了"谁改了什么"的歧义。能用无状态/不可变/单写者解决的问题，就不要引入锁与协调。
4. **数据必须有过硬的一致性证明。** SQLite 有专门的"大巴测试"（随机崩溃后验证数据库可恢复）；PostgreSQL 用 WAL 保证崩溃安全；Redis 提供 RDB/AOF 两种持久化并允许按需取舍。任何持久化系统都要回答：断电、崩溃、并发写时，数据会怎样？
5. **兼容旧数据/旧格式是一种长期投资。** Git 的对象格式十余年不变，迁移成本极低；FFmpeg 二十多年持续支持最老与最新的编解码器。格式变更要支持迁移工具与旧版本读取路径，绝不能默默地让老用户"升级即碎"。
6. **单一职责让人敢依赖你。** curl 只做"用 URL 传数据"，因此被全世界脚本依赖；SQLite 只做嵌入式，因此被手机/浏览器内置。边界越清晰，生态越敢用你。
7. **可观测性是系统软件的出厂配置。** nginx 的错误日志分级清晰；Redis 的 INFO/LATENCY 命令即查即得；PostgreSQL 的慢查询日志与统计收集器随时可查。系统软件必须把诊断能力内置，而不是依赖外部折腾。
8. **长期项目的维护机制是技术活。** FFmpeg 由核心维护者轮换接手二十年；PostgreSQL 有严格的提交评审与测试矩阵；Linux 有分层信任的维护者树。做长期项目时要设计"人员交接、评审流程、回归测试"这三大机制，否则项目会随某个人离开而死亡。

## 项目深拆

### Linux（1991，Linus Torvalds）

**档案**：1991 年 10 月 Linus 在 Usenet 发布 0.02 版内核；1992 年采用 GPL 协议；从"替代 Minix 的个人实验"成长为统治服务器与超算的操作系统内核。

**工程智慧**：
- **先让它跑起来，再让它漂亮**：第一版只支持 386、只有最基本功能，但能跑、能让大家一起玩。社区与协作都是从"能用"开始的，不是从"完美"开始的。
- **分层信任的协作模型**：Linus 只接受 subsystem maintainer 的提交，maintainer 各自把关自己的领域。项目大了以后，用"多级评审 + 明确负责人"代替"所有人审所有事"。
- **兼容性是内核的宪法**：syscall 一旦发布就几乎不能改，这是所有应用敢运行在 Linux 上的前提。给契约上"不可变"属性，换来的生态繁荣远超一时的"整洁"。

**借鉴点**：用"能用版本"快速召集协作者；给模块设 maintainer；把 API/协议当宪法保护。
**易踩坑**：早期过度设计架构（把"可能需要的抽象"提前引入，会让第一版永远出不来）；随意改公共接口（一次破坏性变更会摧毁整个下游生态信任）。

### Git（2005，Linus Torvalds）

**档案**：2005 年 Linus 为管理 Linux 内核、替代收费且有争议的 BitKeeper 而设计；两周内完成核心原型。

**工程智慧**：
- **从"内容"出发设计，而非从"操作"出发**：Git 的核心是内容寻址的对象库（blob/tree/commit 均以内容哈希为 id），所有操作（分支、合并、回滚）都是对象的图操作。数据模型正确，上层一切皆简单。
- **分布式 > 集中式**：每个人都是完整仓库，服务器挂了对开发无影响；这也让"离线开发"与"异步协作"成为自然能力。
- **为真实工作流设计命令**：staging area、rebase、cherry-pick 都是对"工程师实际怎么干活"的建模，而不是对"理想提交模型"的建模。
- **速度是开发体验的一部分**：Git 的操作几乎都只在本地，所以快；Linus 明确把"性能"列为 Git 的设计目标。

**借鉴点**：先定义不可变的数据模型再定义 API；为真实工作流设计功能；本地优先的架构常带来免费的速度与鲁棒性。
**易踩坑**：把版本库设计成"服务器中心"模型（单点故障 + 在线才能协作）；用可变对象建模历史（一旦历史被随意改写，回滚与审计就失去意义）。

### nginx（2004，Igor Sysoev）

**档案**：Igor Sysoev 为俄罗斯门户 Rambler.ru 的高并发场景开发，2004 年公开发布；事件驱动模型让"万级并发"成为默认能力。

**工程智慧**：
- **把并发模型写进架构**：nginx 用异步事件驱动 + 少量 worker 进程替代"每连接一线程"，用极小的内存代价换取极高并发。并发问题的答案在架构层，不在调优层。
- **为真实负载设计**：nginx 的设计起点是 Rambler 实际面对的 C10K 问题——"一万个并发连接怎么办"。问题真实，方案才扎实。
- **配置文件即产品**：nginx 的配置语法对运维友好、可读性极强，这让它成为"工程师愿意亲手部署"的软件。配置/DSL 是面向运维的 UI，值得像产品一样打磨。
- **模块化热插拔**：核心稳定 + 模块扩展，不破坏核心的前提下不断增长能力。

**借鉴点**：做高并发服务时先回答"并发模型是什么"；把"给运维的配置体验"当成一等公民设计；核心与扩展分层。
**易踩坑**：用"每连接一个线程/进程"起步（账户并发一涨就资源耗尽）；把配置设计成只有作者能读懂的"微语法"。

### Redis（2009，antirez / Salvatore Sanfilippo）

**档案**：antirez 为解决创业项目 LLOOGG 的 MySQL 实时统计性能瓶颈而开发，2009 年开源；2010 年起 VMware 赞助全职开发。

**工程智慧**：
- **问题驱动发明**：Redis 不是"造一个数据库"，而是"我的实时统计要快"，痛点到方案只有一步。技术发明的最高成功率来自"自己的痛 + 可交付的窄方案"。
- **单线程 + 事件循环是对复杂度的减法**：单线程免去了大量并发同步问题，换来代码正确性与可预测性；性能靠内存中的数据结构设计取胜，而不是靠多线程。
- **数据结构即 API**：Redis 支持 string/hash/list/set/zset 等，每种操作语义清晰，让"缓存、排行榜、消息队列、分布式锁"都能用一个命令表达。给用户"会说话的数据结构"，比给一堆底层原语强。
- **持久化按需取舍**：RDB（快照）与 AOF（追加日志）让用户在性能与安全之间选择，而不是替用户决定。

**借鉴点**：用真实痛点引导功能；优先用"单线程/无共享"消灭并发复杂度；设计语义丰富的数据结构与操作。
**易踩坑**：把多线程当万能药（引入的竞态与调试成本常超过收益）；提供底层读写原语而不提供高层语义（用户难以正确使用）。

### SQLite（2000，D. Richard Hipp）

**档案**：2000 年由 D. Richard Hipp 发布；嵌入式、零配置、"数据库就是一个文件"，是史上部署最广的数据库引擎。

**工程智慧**：
- **极简模型是最高美学**：整个数据库就是一个磁盘文件，无需服务器、无需配置、无需账号体系。把复杂度的 90% 从用户侧消掉，用户才敢在手机上、浏览器里、嵌入式设备上放心内置它。
- **测试工程是质量的唯一保障**：SQLite 核心代码约 15.6 万行（155.8 KSLOC，version 3.42.0 口径），测试代码与测试脚本约 9.2 万 KSLOC（92053.1 KSLOC，达核心代码的 590 倍），另有数百万测试用例；测试矩阵覆盖每个代码分支、每个平台、每个字节序；"大巴测试"会反复随机崩溃并验证数据库能恢复。系统软件的质量是"测"出来的，不是"写"出来的。
- **明确的单写者语义**：一次只有一个写者、数据库级锁，语义简单透明，反而让"并发写"的问题在应用层可预期。
- **公共领域的授权策略**：SQLite 选择 Public Domain，彻底消除授权摩擦，换来最大规模的采用。

**借鉴点**：把"用户零配置"当作设计目标；为关键路径资产配备远超实现代码量的测试（SQLite 的测试体量约为核心代码的 590 倍）；用明确的简单语义代替复杂的聪明方案。
**易踩坑**：把"嵌入式"悄悄升级成"服务器模式"（功能多了，简单性就没了）；只测正常路径不测崩溃/恢复（对存储类代码是致命疏忽）。

### PostgreSQL（1996 开源，源自伯克利 POSTGRES）

**档案**：1986 年 Stonebraker 在加州大学伯克利分校启动 POSTGRES（Post Ingres）研究项目；1996 年以 PostgreSQL 名义作为开源项目发布；图灵奖得主 Stonebraker 的学术传承在数据库业界影响深远。

**工程智慧**：
- **以学术严谨性做工程**：POSTGRES 出身于研究项目，把"新想法先做原型验证，再落成产品"的路径走成了数据库界的经典样板——很多当年的"研究功能"（如扩展类型、规则系统、MVCC）后来都成了主流数据库标配。
- **扩展性是架构主题**：PostgreSQL 用"关系 + 可扩展类型/函数/索引/操作符"把领域知识留给用户，通用引擎负责事务与查询优化。给用户扩展点，比替用户实现所有功能更能长久。
- **MVCC 让读写不互斥**：多版本并发控制解决了"读不阻塞写、写不阻塞读"的实际痛点，这是它被长事务高并发业务信任的基础。
- **三十年兼容演进的耐心**：SQL 方言兼容是承诺，存储实现可以升级换代。接口与实现解耦是长寿系统的共同特征。

**借鉴点**：把关键机制（如并发模型）先想透再做功能；给用户"可扩展点"而非替用户做完一切；接口承诺要保守。
**易踩坑**：为短期性能牺牲事务语义/一致性（长期必然反噬）；接口频繁破坏性变更（会赶走所有潜在迁移者）。

### curl（1996，Daniel Stenberg 等）

**档案**：1996 年作为 httpget 起源（Rafael Sagula 发起，Daniel Stenberg 参与），1997 年加入 FTP 改名 urlget，1998 年 4.0 版更名 curl；支持 30+ 协议，是脚本与 CI 世界的事实标准。

**工程智慧**：
- **一个工具吃透一个领域**：curl 不做 UI、不做 IDE、不做下载管理器，只把"用 URL 语法传输数据"做到极致，于是成为所有系统集成里唯一被信任的那个组件。
- **CLI 的可用性靠约定与一致性**：`-o`、`-L`、`-X` 等参数的稳定约定 + 各协议行为一致，使用户记忆成本极低。CLI 设计要有全局一致的哲学，而不是每加一个功能就用一个新语法。
- **库与 CLI 分层的艺术**：libcurl 是库、curl 是 CLI，同一引擎服务两种人群。核心能力与产品外壳分离，让"嵌入别人系统"和"人类直接使用"都不妥协。
- **长期维护的稳定性**：20 多年持续维护，协议层出不穷但命令行兼容性保持近乎完美。向后兼容是 CLI 工具的信用。

**借鉴点**：为一个职责做出世界级深度；CLI 参数命名保持全局一致；库/API 与交互工具分层。
**易踩坑**：功能蔓延（curl 从没做下载管理器，这是它活下去的原因之一）；破坏既有参数语义（会让亿级脚本瞬间失效）。

### FFmpeg（2000，Fabrice Bellard）

**档案**：2000 年 12 月 20 日由 Fabrice Bellard 创建并发布（"Fast Forward MPEG"），2004-2015 由 Michael Niedermayer 维护；音视频编解码/转码/流处理的事实标准。

**工程智慧**：
- **在极端兼容里找统一抽象**：FFmpeg 有 libavcodec（编解码）、libavformat（封装/解封装）、libavfilter（滤镜）等清晰分层，几百种格式都映射到统一的数据流模型（AVStream/AVPacket）。要支撑惊人的格式多样性，必须有一个强大的核心抽象。
- **性能是逐字节抠出来的**：ffmpeg 的转码速度来自 C + SIMD 汇编 + 硬件加速的三层优化。系统软件的"快"靠的是架构与底层，不是靠框架魔法。
- **工程民主与继任机制**：项目由核心团队维护，主维护者经历了交接（Bellard → Niedermayer → 团队），这保证项目不被个人绑架，持续迭代二十年。
- **以 LGPL/GPL 双许可平衡**：库可链接（LGPL）、工具可商用（GPL），授权利润差极小，采用面最大化。

**借鉴点**：先定核心数据流抽象再塞兼容层；用"架构 + 底层优化"而非框架技巧获得性能；设计项目继任与多人维护机制。
**易踩坑**：为兼容性让核心模型扭曲变形（抽象一旦崩坏，后续每个特性都加倍昂贵）；代码只一个人能改（一旦离开项目就停摆）。

## 模块速查表

| 项目 | 核心可迁移点 | 一句话提醒 |
|---|---|---|
| Linux | "能用版本"召集社区、分层维护、契约不可变 | 先跑起来，再谈完美 |
| Git | 内容寻址数据模型、分布式、为真实工作流设计 | 数据模型正确，上层全简单 |
| nginx | 事件驱动模型写进架构、配置即产品 | 并发答案在架构层，不在调优层 |
| Redis | 单线程减法、数据结构即 API、问题驱动发明 | 用痛点到方案，不造无场景的轮子 |
| SQLite | 极简模型、测试驱动质量、单写者语义 | 简单是最高美学，测试是唯一保障 |
| PostgreSQL | 学术原型落地、扩展点、MVCC、接口兼容 | 接口承诺保守，内部敢于演进 |
| curl | 单一职责、CLI 一致性、库壳分层 | 一个职责做透，全世界都敢依赖你 |
| FFmpeg | 统一核心抽象、分层优化、继任机制 | 兼容多样性靠强抽象，不靠堆分支 |

## 一句话提醒

这一层的项目证明：**系统软件的胜利 = 正确的模型（并发/存储/数据）+ 稳定的契约 + 过硬的测试与可观测性**。做任何底层组件，先在这三件事上投入，功能只是时间问题。
