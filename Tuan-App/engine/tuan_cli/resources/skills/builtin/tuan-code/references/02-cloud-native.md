# 模块二 · 容器与云原生（8 项目）

**模块定位**：当你要设计微服务、容器化、编排平台、可观测性体系、基础设施即代码时使用。这一代云原生项目回答的核心问题是：**如何把"运行软件"本身变成可声明、可编排、可观测的工程对象**。本模块蒸馏 Kubernetes、Docker、etcd、Prometheus、Grafana、ClickHouse、Terraform、Ansible 的共同规律。

## 核心法则

1. **声明式 > 命令式。** Kubernetes 用"期望状态"（desired state）作为系统核心——你声明"我要 3 个副本"，系统负责"把它变成现实并保持"。Terraform 的 plan/diff 让基础设施变更可审阅、可回滚。声明式接口简化用户心智，把"如何做"留给系统。
2. **标准接口 = 生态的肥沃土壤。** Docker 定义了镜像与容器运行时标准，于是整个容器生态能在其上生长；CNI/CSI/CRI 让 Kubernetes 的存储、网络、运行时都可插拔。制定"小而准的接口标准"，比实现"大而全的功能集"更能赢得生态。
3. **一致性协议要选对实现，不要自己发明。** etcd 实现了 Raft 共识算法，作为"分布式的 /etc"提供强一致的键值存储；Kubernetes 的 API server 依赖它保证集群状态一致。分布式一致性是极难做对的领域，能用成熟实现就不要自己造。
4. **可观测性是系统的一等公民。** Prometheus 把指标采集设计成"服务主动暴露 + 服务器拉取"的 pull 模型，服务端无须侵入业务代码；Grafana 让指标可视化成为运维日常。"日志、指标、追踪"三类信号缺一不可。
5. **围绕真实痛点定义性能目标。** ClickHouse 不为通用 OLTP 设计，它只为"分析型查询在大数据量上的秒级响应"这一个目标服务，用列式存储 + 向量化执行达到极致。性能目标越尖锐，实现越能一招制敌。
6. **配置/代码的语义要贴近领域。** Terraform 的 HCL 让你"描述基础设施"而不是"调用 API"；Ansible 的 YAML 剧本让非程序员也能看懂运维动作。DSL/配置层的核心价值是"消除心智翻译"。
7. **自举与dogfooding。** Kubernetes 用自身托管自身（kubeadm 自举集群）；Prometheus 用自身监控自身。敢用自己产品的系统，会更快暴露并修掉真实缺陷。
8. **给用户一条"升级/迁移"的活路。** 云原生工具链演进极快，真正长期胜出的项目都提供清晰的版本策略、废弃窗口与迁移路径，而不是用破坏性变更绑架用户。

## 项目深拆

### Kubernetes（2014，Google）

**档案**：Google 基于内部 Borg 系统的十多年容器编排经验，2013 年立项、2014 年 6 月开源；2015 年捐赠 CNCF，成为容器编排事实标准。

**工程智慧**：
- **把十年内部经验提炼成公开产品**：Borg 在 Google 内部跑了十余年，Kubernetes 从第一天起就带着"大规模生产验证过"的设计——pod、service、label、controller 无一不是从真实调度痛点里长出来的。从内部系统到开源产品是极强的方法论：先内部打磨，再对外开源。
- **Control Plane 的声明式循环**：API server + etcd + controller 构成"观察-比较-纠正"的控制回路；用户只描述期望状态，控制器负责收敛。这种设计让系统自愈成为默认行为而非特殊功能。
- **以 API 资源为核心建模一切**：Pod、Deployment、Service 都是 REST 资源，扩展（CRD）也遵循同一模式——统一 API 层让"新能力"接入成本极低。
- **接口即标准**：CRI（容器运行时）、CNI（网络）、CSI（存储）三大接口让 Kubernetes 保持内核稳定、外围繁荣。

**借鉴点**：用"期望状态 + 控制器"模式设计自愈系统；先提炼内部生产经验再产品化；用标准接口划分"稳定内核"与"开放生态"。
**易踩坑**：把控制回路设计成命令式（用户"手动执行"而非"声明期望"，系统就无法自愈）；让 API 依赖具体实现细节（接口一变，生态全碎）。

### Docker（2013，Solomon Hykes）

**档案**：dotCloud 内部项目，2013 年 3 月 Apache 2.0 开源；以"镜像 + 容器"标准化了打包与交付，2013 年底 dotCloud 更名 Docker。

**工程智慧**：
- **一个统一概念化解交付难题："Build, Ship, Run"**：Docker 没有发明容器技术（chroot/cgroups 早已存在），它做的是把容器的"打包、传输、运行"统一成一个工具与一种镜像格式，让"在我的机器上能跑"成为历史。
- **开发者体验即护城河**：`docker run`、`docker build` 的极简心智模型让任何开发者 10 分钟内上手；Dockerfile 让环境配置变成可版本化的代码。面向开发者体验打造产品，传播速度是指数级的。
- **分层镜像作为缓存与传输的基石**：镜像层复用（Union FS）让几百 MB 的镜像可以增量传输、分钟级构建，解决了"交付体积/速度"这个实际工程问题。聪明的底层设计带来显性体验收益。
- **少即是多**：Docker 只做"打包 + 运行"这一件事的标准化，不做容器调度（那是 Kubernetes 的事），反而成就了生态分工。

**借鉴点**：把已有的"底层技术"用"一个统一心智模型"包装成大众产品；开发者体验是传播引擎；分层/增量是传输与大文件问题的最优解。
**易踩坑**：在"标准格式"尚未稳定时就铺生态（生态会在格式变更时崩盘）；替用户做完所有事（调度、编排全自己做，就失去了与生态协作的空间）。

### etcd（2013，CoreOS）

**档案**：CoreOS 2013 年 6 月发起，用 Go 实现 Raft 共识算法，提供强一致的分布式键值存储，是 Kubernetes 存储集群状态的基石。

**工程智慧**：
- **做"分布式的 /etc"**：etcd 的定位不是通用数据库，而是"集群配置与状态的权威来源"。定位清晰的系统，选型、实现、性能目标全部服从于这个定位。
- **让共识算法成为产品卖点而非黑匣子**：etcd 把 Raft 实现了文档化、可测试、跨语言可参考的范本（raft 库可独立使用）。当你做"别人不敢做对的难事"（分布式一致性），得到的信任是最深的。
- **强一致性换来简单上层**：Kubernetes 之所以敢把所有状态都交给 etcd、让控制器只看一个事实源，正是因为 etcd 提供强一致读写。
- **watch 机制支撑事件驱动架构**：etcd 的 watch 让上层能订阅变化，不轮询——事件驱动系统的事实源到位，控制器模式才能成立。

**借鉴点**：用成熟共识算法实现做一致性的基座；提供 watch/订阅原语让上层做事件驱动；把复杂组件文档化到"别人能参照理解"。
**易踩坑**：自己发明共识算法（极难正确，且调试代价巨大）；把强一致系统当高性能缓存用（语义错配会让两边都糟糕）。

### Prometheus（2012，SoundCloud）

**档案**：SoundCloud 2012 年为解决微服务监控问题开发，后捐赠 CNCF；pull 模型 + 多维数据模型的指标监控事实标准。

**工程智慧**：
- **pull 模型重塑监控范式**：Prometheus 让被监控服务只需"暴露 /metrics"，监控服务器主动拉取；这消灭了"业务代码主动上报"的侵入性，也让"服务没起 = 指标缺失"成为天然探活信号。
- **用"指标名 + 标签"建模多维数据**：一条时序 = 指标名 + 键值标签，查询（PromQL）可以按任意维度聚合。给数据一个灵活的维度模型，比预置固定报表强得多。
- **声明式告警规则 + 告警管理器**：规则文件用声明式语法描述"什么条件触发告警"，告警去重/分组/静默在 Alertmanager 中集中处理。把"策略"和"机制"分离。
- **自举与生态分工**：Prometheus 自己监控自己；服务发现（Consul/K8s 等）与长期存储（Thanos/Cortex）交给生态。

**借鉴点**：监控设计成"标准端点 + 拉取"而非侵入式 SDK；用标签维度模型让查询灵活；规则声明化、机制与策略分离。
**易踩坑**：让业务代码直接连监控后端（耦合 + 单点）；把指标设计成"固定报表"（用户一有新问题就要改代码）。

### Grafana（2014，Torkel Ödegaard）

**档案**：Torkel Ödegaard 因对 Graphite 的仪表盘不满意而创建，2014 年开源；如今是开源界最普及的可视化面板。

**工程智慧**：
- **"比现有选择好 10 倍"的切入点**：Grafana 不做数据存储、不做告警引擎，只把"可视化面板"这一环做到远超同类——一个不满意的开发者的个人项目，成了业界标准。找到链条上最痛的一环，做透它。
- **插件与数据源抽象**：Grafana 通过"数据源"插件接入几十种存储（Prometheus、InfluxDB、SQL、云厂商），面板与数据源解耦。面向扩展设计，让生态替你覆盖长尾。
- **可组合的 UI 组件化**：面板、变量、模板、分享链接，把运维看板做成了可复用、可分享的"工程对象"。

**借鉴点**：选择生态链条上"最痛且可独立交付"的一环做透；用插件抽象吃掉长尾集成；把 UI 做成可组合的组件。
**易踩坑**：把存储/告警/可视化全自己做（每个领域都有更强对手，摊薄会让每个都平庸）；闭门造车不接数据源生态（集成能力决定采用速度）。

### ClickHouse（2009 开发 / 2016 开源，Yandex）

**档案**：Yandex 为 Yandex.Metrica（网页分析）的海量事件分析而开发，2016 年 Apache 2.0 开源；列式存储 + 向量化执行的 OLAP 标杆。

**工程智慧**：
- **为单一尖锐目标优化**：ClickHouse 只回答"分析查询在海量数据上要快"，于是敢用列式存储、向量化执行、稀疏索引、数据压缩这些"为读优化"的激进设计。目标尖锐，方案才敢决绝。
- **先有真实数据规模，再有性能设计**：Yandex.Metrica 每天产生数百亿事件，这是任何 benchmark 都无法提供的真实压力。没有真实数据规模，性能优化就是猜。
- **物化视图下沉计算**：把聚合结果预计算、查询时只读结果，是"大查询快"的秘密。能用预处理换查询速度时，坚决用。
- **分布式表与副本透明化**：分布式表对一个逻辑表透明地路由到多分片多副本，用户写同一套 SQL——分布式的复杂度被封装在引擎内部。

**借鉴点**：性能目标要"尖锐到敢用激进架构"；用真实数据规模驱动优化；预计算/物化是读密集系统的核心手法。
**易踩坑**：试图用列存引擎做通用 OLTP（写入路径和点查询会很难受）；把"查询快"寄托在缓存而非存储模型上（缓存一冷就露馅）。

### Terraform（2014，HashiCorp）

**档案**：HashiCorp 推出的声明式基础设施编排工具，用 HCL 描述云资源，"代码审查 + 计划 + 应用"的工作流让基础设施变更可治理。

**工程智慧**：
- **声明式 + 状态文件 = 基础设施的 Git**：Terraform 维护状态文件（terraform.tfstate），与真实世界 diff 后生成执行计划（plan），用户可以审阅"将要发生什么"再应用。把"基础设施"变成可 diff、可回滚、可评审的对象，是 IaC 的灵魂。
- **DSL 贴近领域（HCL）**：HCL 描述"我要什么资源、什么配置"，表达力与可读性平衡，让基础设施代码像"文档"一样可读。
- **Provider 插件化吃掉云厂商长尾**：几百个云服务通过 provider 接入，核心引擎只负责"图计算 + 计划执行"。核心稳定、生态扩张。
- **幂等与收敛**：同样的配置应用两次结果一致，这是声明式系统被信任的前提。

**借鉴点**：重要变更先"计划/评审/预览"再执行；用状态 + diff 实现可治理；核心引擎与外围 provider 分层。
**易踩坑**：状态文件管理混乱（多人同时 apply 会互相覆盖；必须上锁/远程状态）；配置与实际资源漂移（drift）后无人收敛。

### Ansible（2012，Michael DeHaan）

**档案**：Michael DeHaan 2012 年创建，2015 年被 Red Hat 收购；无代理架构 + YAML 剧本让运维自动化对团队友好。

**工程智慧**：
- **无代理架构 = 零安装成本**：Ansible 通过 SSH 直接操作远程主机，目标机器不需要预装 agent。把"采用成本"砍到最低，是工具快速扩张的关键。
- **人类可读的 YAML 剧本**：playbook 是"可读的叙事"（装什么、配什么、起什么），运维能看懂、非工程师也能审阅。DSL 的可读性直接决定协作半径。
- **幂等模块**：每个模块声明"确保状态"，重复执行结果一致。幂等让自动化可以安全地反复运行，这是自动化信任的基础。
- **从命令到剧本的演进路径**：ad-hoc 命令 → 剧本 → 角色/集合，用户随复杂度平滑升级，学习曲线平缓。

**借鉴点**：采用成本（agent 安装）是工具传播的隐形门槛，能省则省；配置胶水语言要人类可读；所有自动化操作幂等。
**易踩坑**：让自动化"只管执行不管状态"（重复跑会出错/漂移）；剧本写成一次性脚本（无法复用，也无法审阅）。

## 模块速查表

| 项目 | 核心可迁移点 | 一句话提醒 |
|---|---|---|
| Kubernetes | 声明式控制回路、接口标准、内部经验外化 | 描述期望状态，让系统自愈 |
| Docker | 统一心智模型、镜像分层、开发者体验 | 包装底层技术为大众产品 |
| etcd | 成熟共识算法、强一致事实源、watch 原语 | 一致性用成熟实现，别自己发明 |
| Prometheus | pull 模型、标签维度、规则声明化 | 监控是标准端点，不是业务代码 |
| Grafana | 找准最痛一环做透、数据源插件化 | 做链路上最强的一环，其余交给生态 |
| ClickHouse | 尖锐性能目标、列存+向量化、物化视图 | 为一件事做到极致，敢用激进架构 |
| Terraform | 声明式+状态diff、HCL、provider 生态 | 变更先计划后执行，状态要上锁 |
| Ansible | 无代理、YAML 可读、幂等模块 | 采用成本为零，自动化就可信任 |

## 一句话提醒

这一层的项目证明：**云原生时代的胜负手 = 声明式接口 + 标准生态 + 可观测性 + 极低采用成本**。设计平台型系统时，先想清楚"用户要声明什么，系统负责什么，生态如何接入"。
