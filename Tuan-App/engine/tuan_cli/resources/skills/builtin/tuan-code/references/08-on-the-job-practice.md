# 模块八 · 线上工程实战：真实事故复盘与一线经验（4 事故 + 7 专题）

**模块定位**：前七个模块教你"把软件做出来、做对"，本模块教你"把系统活着运营"。这里不蒸馏开源项目的代码，而是复盘四起真实生产事故——Knight Capital（2012）、AWS S3（2017）、GitLab（2017）、GitHub（2018），并给出变更管理、回滚、事故复盘、性能排查、迁移、代码评审、稳定性工程七组一线实操经验。**事实与经验法则的区分约定：文中"【事实】"标记的内容来自公开事故报告（SEC、AWS、GitLab、GitHub 官方公告），可按原文溯源；"【经验法则】"是从多个事故中归纳的可迁移做法，不是任何单一项目的承诺，迁移到你的环境时需重新评估。** 引用格式：[0N-项目名] 指某模块深拆、[0N-核心法则 N] 指模块法则、[心法 N] 指总纲十条（见 SKILL.md）。

## 核心法则

1. **生产事故的第一根因常常不是"代码写得差"，而是"变更流程没守住"。** Knight Capital 的 RLP 新代码在 8 个月内通过了一轮轮功能测试，真正杀死它的是部署环节——新代码只上到 8 台服务器中的 2 台，其余 6 台仍跑着该退休的旧代码，并在新的外部参数下激活了本应停用的交易逻辑。代码是部署流程走完之后的产物：**先审查流程，再审查代码**（对应 [01-核心法则 8] 维护机制）。

2. **回滚预案必须在变更生效前写好，不是事故后现写。** Knight 在疯狂的 45 分钟里找不到一键关闭错误逻辑的手段；AWS S3 团队此刻按手册执行的操作又带着错误的参数。任何变更提交前，必须回答三个问题：怎么发现它坏了？怎么把能力退回上版本？退不回去时怎么止血？

3. **可观测性决定事故的影响半径。** GitHub 的 43 秒网络分区本身不是灾难——灾难是分区让自动故障转移工具误判、团队没能立刻看到"两个主库都在收写"的关键信号。[01-核心法则 7] 的可观测性在事故语境下不是"方便排障"，而是"决定你能在多大范围内止血"。

4. **操作手册（playbook/runbook）也要像代码一样被评审和防呆。** S3 事故的直接操作确实是"按手册删服务器"，错的是手册里的参数导致删多了。能挡住手误的不是"让人更小心"，而是防呆设计：危险命令先 dry-run、自动校验参数范围、操作前打快照（与 [02-Terraform] 的 plan/apply 分层同构）。

5. **数据库备份的验收标准是"能恢复"，不是"有备份"。** GitLab 有备份，但从未做过端到端恢复演练：备份进程实际因内存问题从未成功完成过、pg_dump 版本与生产不匹配、备份目录磁盘已满——三层缺陷叠在一起，事故当天才发现"备份等于没有"。**定期做"备份 → 新环境 → 恢复 → 校验"演练，恢复了才算数。**

6. **分布式高可用工具在分区下可能放大事故，而不是兜底。** GitHub 的 Orchestrator 在短暂分区时连续发起主备切换，最终制造出"两个节点都认为自己可接受写入"的歧义，把 43 秒的分区变成了 24 小时的对账。高可用工具必须把"防脑裂"（quorum/fencing，仲裁丢失即降级只读）当作一等公民，而不是默认信任（对应 [01-核心法则 3] 状态共享）。

7. **事故复盘是生产系统的迭代机制，追责是复盘的毒药。** 四起事故都有明显的人为环节，但根因都在系统设计——没有 kill switch、没有防呆、没有恢复演练。复盘的价值是把"人的错误"翻译成"系统的改进项"，让下一次事故发生在更远的地方。

8. **稳定性是持续投入的工程，不是上线前的一次性检查。** 事故不会因为你"这次很小心"而消失，只会转移。要建立可度量的稳定性目标（SLO/error budget）、定期演练（game day）、随时可执行的 runbook，把"防事故"变成常规研发节奏的一部分。

## 事故深拆（案例为已核实事实）

### Knight Capital（2012-08-01，美国）

**档案（已核实事实）**：
- 【事实】2012 年 8 月 1 日，Knight Capital（当时美国最大的做市商之一）部署面向零售流动性项目（RLP）的新代码，目标 8 台服务器。
- 【事实】新代码只部署到 2 台服务器；其余 6 台未移除的旧代码在新的外部参数下被激活（本应停用的旧交易逻辑开始向市场发出大量错误买卖单）。
- 【事实】故障自开盘后持续约 45 分钟，Knight 累计亏损超 4.6 亿美元（SEC 事后调查报告口径），远超其市值，随后被迫接受 Getco 收购（合并为 KCG）。
- 【事实】SEC 报告指出：RLP 代码此前经过了约 8 个月的功能测试，但**部署流程控制失败**——没有验证"全部节点都跑到新版本"，没有在新旧代码混跑时阻断交易。

**工程智慧**：
- 部署的目标是"集群状态一致"，不是"把包发出去"。要有明确的版本一致性检查：全部节点确认新版本 running、旧能力确认下线后，才认为部署完成。
- 交易/写入/对外副作用类功能必须保留**紧急停用开关（kill switch）**——不是"关掉服务"，而是"停掉错误行为"（呼应 [心法 9] 可观测与可控制）。
- **新旧代码混跑比全挂更危险**：它不报错，只是行为错误。灰度必须配行为对照（新旧结果比对），不只是"看它还活着"。

**借鉴点**：生产变更要有"全量确认 + 混跑检测"；对外副作用（真实交易、发消息、写生产数据）默认视为危险行为，出错时默认不自动重试。
**易踩坑**：把功能测试通过等同于部署成功；把"灰度"等同于"分批发布而不比较行为差异"；没有 kill switch 时把希望寄托在"人工盯盘"。

### AWS S3（2017-02-28，US-EAST-1）

**档案（已核实事实）**：
- 【事实】2017 年 2 月 28 日 09:37 PST，AWS S3 团队为排查计费系统处理变慢，按运维手册执行"删除少量服务器"的操作。
- 【事实】命令中的参数输入有误，删除了比预期更多的服务器，导致两个关键子系统——索引子系统（index）与放置子系统（placement）瘫痪。
- 【事实】S3 的请求必须先查索引子系统才能定位对象，恢复必须先重建索引；重建期间大量依赖 S3 的 AWS 服务与外部客户（含 Netflix 等）受连带影响，恢复耗时数小时（AWS 官方公告口径）。
- 【事实】AWS 事后将根因归为"操作错误 + 手册防呆不足"，并承诺加强危险操作确认机制。

**工程智慧**：
- 对共享基础设施的**批量破坏性操作**要假设"人必会输错"。正确做法：先 dry-run、自动校验参数范围、操作前后打快照（与 [02-Terraform] 的 plan/apply 分层同构）。
- 关键路径必须考虑"重建时间"：S3 索引是必须重建才能服务的状态，"重建是长尾"的子系统要设计多级冗余、分片恢复，而不是单一全量重建。
- 事故的爆炸半径取决于**共享度**：一个看似不起眼的计费子系统下线，会波及其上所有依赖方。变更影响评估要按"依赖我的系统"画出来，不只按"我依赖的系统"。

**借鉴点**：破坏性命令默认 dry-run + 参数范围校验 + 快照回退；把"重建时长"纳入系统与备份设计；变更评审要列出下游依赖方。
**易踩坑**：用"操作正确"赌手误；没有对生产破坏性命令做二次确认；把运维手册当成"写了就安全"（手册本身要版本化 + 评审，对应核心法则 4）。

### GitLab（2017-01-31）

**档案（已核实事实）**：
- 【事实】2017 年 1 月 31 日，GitLab 工程师在迁移数据库（db1 主库 → db2 备库同步）期间，在错误的节点上执行了删除数据目录的命令，生产主库 db1 的数据被删除（约 300GB）。
- 【事实】删除与同步任务并行进行，导致约 6 小时的 issues、comments、merge requests 等数据丢失。
- 【事实】尝试从备份恢复失败：备份进程此前从未成功完成过（内存问题）、pg_dump 版本与生产环境不匹配、备份目录磁盘空间不足——多重机制缺陷叠加，备份形同虚设。
- 【事实】GitLab 全程公开恢复过程（直播 + 公开 postmortem），成为业界"透明复盘"的经典样本。

**工程智慧**：
- **备份的要义是"定期恢复演练"**：一次从未演练过的备份，在灾难当天大概率不可用。恢复演练应纳入运营节奏（对应核心法则 5）。
- 高风险数据库操作的三大护栏：**错库识别**（操作前显示当前库名/节点并要求显式确认）、**禁止用 shell 裸命令删数据库目录**（走受管流程）、**并发任务隔离**（同步与删除不能在相邻节点上并行）。
- 事故透明本身是工程资产：GitLab 公开直播与复盘，换来社区信任与全行业的学习材料；对内，透明复盘让改进项真正落进团队记忆（[01-核心法则 8] 维护机制）。

**借鉴点**：数据目录的删除/重建必须走受管工具而非 shell 裸命令；备份恢复要做"新环境演练"；为数据库高危操作设计"当前节点显式展示 + 二次确认"。
**易踩坑**：把"备份脚本能跑出文件"当成"备份可用"；恢复依赖与生产完全一致的版本与磁盘空间，演练时就要核对；对"只影响测试库"的侥幸心理（db1/db2 命名相似本身就是事故隐患）。

### GitHub（2018-10-21）

**档案（已核实事实）**：
- 【事实】2018 年 10 月 21 日 22:52 UTC，GitHub 工程师更换连接两个数据中心的一块 100G 光模块，更换期间两个核心网络设备间出现约 43 秒的分区。
- 【事实】该分区触发了 GitHub 的 MySQL 高可用工具 Orchestrator 发起主备切换；受网络拓扑变化与切换时序影响，集群进入"两个节点都认为自己可接受写入"的歧义状态（双主写）。
- 【事实】为避免数据不一致扩大，GitHub 先停服降级，随后用 24 小时 11 分钟人工对账修复，最终**无数据丢失**（GitHub 官方 postmortem 口径）。
- 【事实】事后改进包括：用"全数据中心级故障"演练验证故障转移逻辑、为 Orchestrator 增加分区识别、把恢复阶段的条件判断自动化。

**工程智慧**：
- **故障转移工具的失效模式要写进故障演练**：Orchestrator 本意是兜底，却在"分区 + 拓扑变化"组合下制造了更严重的一致性歧义。高可用不等于自动 failover，要明确"什么条件下禁止自动切换"（仲裁丢失时只读不写，[01-核心法则 3] 状态共享）。
- **分区是分布式系统最危险的输入**：43 秒的短暂分区若没有任何写入，本可无感知；一旦分区期间有写 + 自动切换，就变成分裂脑。主写节点必须持有"租约/quorum"，失去仲裁立即降级只读（fencing）。
- **"无数据丢失"与"快速恢复"在一致性事故下往往不可兼得**：GitHub 选择保数据，代价是 24 小时的人工对账。事故预案要提前定好这个取舍，而不是灾难现场讨论（呼应 [心法 10] 迭代要快、契约要慢）。

**借鉴点**：给自动化工具写"失效模式清单"（网络分区、时钟偏移、双主同时存活）；把"仲裁丢失时的降级行为"写进数据库集群配置；演练要覆盖"工具在故障下的行为"，不只演练"服务的恢复"。
**易踩坑**：把高可用工具当黑盒信任；只演练 happy path（主挂了切备），不演练"分区 + 自动切换叠加"；以为"有副本"就等于"不会丢一致性问题"（副本也会分歧）。

## 实操经验（经验法则，按 ADR 背景 / 决策 / 结果组织）

### ADR-101 变更管理：任何生产变更先做"变更四问"

- 背景：四起事故全部发生在"变更"期间（部署、换设备、删服务器、数据库同步），没有一次是"系统突然自身坏掉"。
- 决策：对每个生产变更（代码、配置、数据、基础设施）强制回答四问——①影响面（这次会碰到什么状态/对外行为）；②可观测（失败时靠哪块监控/告警发现，指标名写下来）；③可回滚（代码与数据分别怎么退回上一版本）；④验证标准（怎么证明变更成功，数字验收）。
- 结果：四问写进变更单与 PR 模板后，"变更风险"从隐性变成显式；S 档小变更也至少口头回答③④两问。

### ADR-102 回滚三角：止血 → 容量回退 → 数据补偿

- 背景：Knight 没有 kill switch；S3 删错了服务器却要先重建索引；GitLab 想恢复却无可用备份。共同点：把"恢复"拖到了灾难现场。
- 决策：任何变更自带"回滚三角"预案——①止血（kill switch/熔断/禁写，先停住错误行为，不追求已发生的损失立即消失）；②容量回退（把代码/配置退回最后已知良好版本，[01-Git] 的 revert 与廉价分支保证这一步随时可做）；③数据补偿（对回退期间产生的错误数据写补偿任务，按影响面分批执行）。
- 结果：预案写在变更文档里，事故时按顺序执行而不是现场思考；未写回滚方案的大型变更不允许进生产（[心法 7] 破坏性变更按版本阶梯释放同理）。

### ADR-103 事故复盘：blameless + 时间线 + 行动项

- 背景：追责式复盘让当事人隐瞒细节，根因永远查不清；GitLab/GitHub 的公开复盘之所以有学习价值，是因为时间线客观、行动项具体。
- 决策：复盘固定结构——①背景（变更、what、why）；②时间线（逐条客观事件，含"发现-通报-处置"三列）；③根因（区分直接原因与系统性原因，5 Whys 追问到流程/设计）；④影响（时长、数据、用户、恢复代价）；⑤行动项（owner + 期限 + 验收方式，**禁止"加强意识"这类不可验收项**）。
- 结果：复盘产出的是"下一次事故更远"的改进项清单，不是责任认定；行动项进入排期，3 个月内复查完成率。

### ADR-104 性能排查：先指标，后日志，再 profile

- 背景：性能问题最常见的错误是"猜"——猜缓存、猜 GC、猜锁，然后瞎改。[01-核心法则 7] 的可观测性在不被使用时等于没有。
- 决策：固定排查顺序——①看指标曲线（CPU/内存/IO/网络/GC/连接池/QPS/延迟分位），先定位"哪个资源到顶"；②看日志与追踪（慢查询、错误堆栈、trace 链路，定位到具体调用路径）；③profile（CPU/内存采样，验证假设）；④改一处、复测一处，记录前后分位延迟。指标面板与告警不在排查时搭，在平时搭（[心法 9]）。
- 结果：把"性能排查"变成可复制的 checklist，而不是依赖个人经验；每次排查留下"假设-验证-结论"记录，积累成团队的性能知识库。

### ADR-105 迁移：影子读 → 双写 → 切换，且每一步可回退

- 背景：数据库或服务迁移是生产事故高发区（GitLab 就在迁移现场出事）。迁移的本质是"换依赖"，换依赖的本质是"新旧并存期的正确性"。
- 决策：迁移分四步且每步闸门可回退——①影子读（新系统只读旧数据，对比结果 diff，先证明"读得一样"）；②双写（新旧同时写入，核对一致性，先证明"写得一样"）；③切换读/写（旧系统保持短期可回退兜底）；④回收旧系统（观察期过后再删）。任一步 diff 不通过即停在原地修，不硬推进。
- 结果：迁移的验收标准是"新旧系统结果一致 + 回退路径完好"，不是"新系统上线成功"；大规模迁移前必须做一次全量演练（换新环境恢复，对应核心法则 5）。

### ADR-106 代码评审：评审设计决策，不评审代码风格

- 背景：评审低效的两种极端——只挑格式/命名（没价值），或只看不评（走过场）。评审的真正价值是"把设计决策放到多人眼前"。
- 决策：评审清单按优先级——①行为正确性（边界、失败路径、异常处理）；②变更范围（是否超出 PR 声明目标，[心法 8] 少即是多）；③可测试性（代码是否容易为它写测试）；④可回滚性（这个改动能不能安全 revert）；⑤可读性（下一个维护者 6 个月后能否看懂）。风格问题交给格式化工具与 linter（[04-Rust] 工具链理念），人的注意力留给设计。
- 结果：评审从"挑毛病"变成"设计对话"；要求"每个 PR 说明为什么这样设计 + 为什么不用备选方案"，评审质量与新人成长同步提升。

### ADR-107 稳定性工程：SLO 要可度量、演练要定期、runbook 要可执行

- 背景：没有度量就没有稳定性目标，"我们很稳定"无法被验证；没有演练的 runbook 在事故现场大概率失效。
- 决策：①为关键路径定义 SLO（可用性/延迟分位/错误率，要给具体数字）与 error budget，超预算即收紧变更；②每季度一次 game day：人为注入故障（杀节点、封网、降配额），演练发现、通报、处置、恢复全流程；③runbook 用"操作指令"而非"背景描述"写——每一步执行什么命令、结果长什么样算成功（[01-核心法则 7]）；④on-call 与值班要有明确升级路径（15 分钟无响应 → 通知一线负责人）。
- 结果：SLO 让"稳定性"进入产品决策（开发新功能 vs 偿还稳定性债）；game day 会把"以为会工作"的环节暴露成"已验证会工作"。
