8发现的问题清单（按严重度）

高 core/dynamic_workflow.py:376 闭包里引用未定义的 exc

ruff F821 报 str(exc)，而 exc 在那个 _fail_pool 闭包作用域里不存在。走到动态工作流失败分支时大概率抛 NameError——本应上报失败，结果变成二次异常。这条建议优先复现确认。

中 三处闭包晚绑定（ruff B023）

core/agent.py:916（lambda 抓 tool_calls）、core/dynamic_workflow.py:343（step_idx）、ports/transcript/history.py:251（step）。Python 闭包按名字晚绑定，循环里建的 lambda 实际取调用时的值，多步重试/动态加步骤时可能拿到错的那一轮。

中 qxt doctor 无错误也返回 exit 1

实测"发现 2 个警告，无错误"时退出码是 1。CI/脚本里 qxt doctor && ... 会把"只是缺配置"当成失败。

中 文档数字滞后

README 正文 + security-ci.yml 注释都写"1083 个绕过载荷"，实际矩阵 2310。不影响功能，但对外引用会被人抓把柄。

低 测试里重复定义用例

tests/test_security_enhancement.py 的 test_search_no_results 写了两遍（210/217），第一个永远跑不到；codedev/verify.py:95 字典重复 key "E501"（后者覆盖前者，死配置）。

低 ruff 存量 7431 条

95% 是 PEP585/604 现代化写法，ruff --fix 一把能修掉 5823 条。不是债的利息高，是一直没还。

9总评

把它当成一个"认真做安全的开源终端 Agent"来看，完成度是够的：微内核架构干净、依赖策略克制、11 分钟的测试套件全绿、安全基准真能一条命令本地复现且数字不注水。这几点放在同类项目里是上游水准。

但它还不是可以闭眼发 1.0 的状态。上面那几处真 bug（尤其 exc 未定义和三个闭包晚绑定）是会在生产失败路径上咬人的；文档和 CI 数字没同步、pip-audit 不阻断，属于"工程纪律已经有了，最后一公里没踩实"。建议发布前先修第 8 节里高/中那 4 条，跑一遍 ruff --fix，再把 README 的 1083 改成 2310——都是半天的活，改完这个项目的可信度会上一个台阶。

一句话给选型的人：如果你要的是"危险命令执行前真敢拦、拦了还能撤、换模型不锁死"的本地 Agent，它值得试；安全数字我验过，是真的。但别在没修那几个失败路径 bug 之前，把它接进自动化流水线上跑无人值守任务。

测评：从 0 实测，未沿用任何既往结论。所有命令、计时、测试与安全数字均为本日本机实际运行产出。 产物校验：跑完 git diff bench/security-bench.json 为空，CI 门禁存档未被覆盖；仓库 git status 除用户原有的 bench/ps_safety_report.html 外无新增改动（本报告 html 本身除外）。 未测：一切需 API key 的 LLM 对话/自主循环/TUI 交互，均如实标注，未编造。
