# 系统化调试

90% 的「修不好」是因为在没定位根因前就动手改。先懂，再动。

## 原则
- 不猜，证伪。每步提出一个可证伪假设，用最小动作验证它。
- 一次只改一个变量。同时改三处，你永远不知道哪处生效、哪处埋雷。
- 复现是前提。复现不了的 bug 先记录线索，别急着「应该修好了」。

## 流程
1. 精确描述症状：「在什么输入/操作下，期望 X，实际 Y」，而不是「它崩了」。
2. 读报错，从栈底（最贴近你代码的帧）往上看，别只看最顶的库内部。
3. 二分定位：用日志/断点把可疑区一分为二，逐步缩小到出错的那一行。
4. 看数据的真实形态：打印实际传入的值，常发现比想象的多一个 None / 少一层嵌套。
5. 最小复现：抽一段独立脚本复现，排除干扰后才改——修得快且不易误伤。

## 工具
- 日志分层（debug/info/error），关键分支都留可观测性，而不是靠脑补。
- find_references 确认「谁改了这个值」。
- 回归测试：修完后写一个会失败的测试，证明你真的懂了根因。

## 心态
- 相信证据，不相信记忆。「以前没问题」=「以前没走到这条路径」。
- 卡住就写下来讲给自己听（橡皮鸭）：讲清假设，答案常自己冒出来。
