# code-architect：给代码开发 Agent 的超级工程方法论

## 本技能是什么

这是一套从 **45 个顶级开源项目**里蒸馏出的工程方法论系统。它的假设是：好软件不是靠灵感写出来的，而是靠一套可复用的决策模式——在正确的时间做正确的取舍。Linux、Git、Redis、PostgreSQL、Kubernetes、LLVM、Rust、Vite……这些项目各自解决了不同的问题，但它们的成功背后有大量重叠的工程智慧。本技能把这些智慧提炼成法则、工作流与检查清单，使任何代码开发 Agent 在接手任何软件工程任务时，都能站在这些项目积累的经验之上，而不是每次从零试错。

**使用方式**：先读本文件的十条心法总纲与路由表，确定任务类型；再进入对应 `references/` 模块读深度蒸馏；最后按标准工作流执行，用终检清单收尾。整套系统以"为什么这样做"为主线——理解了原因，Agent 才能在其他任务上迁移应用。

## 十条工程心法（总纲）

以下十条从全部 45 个项目中提炼，是所有模块的共同底座。执行任何任务前先过一遍这十条，再进入具体模块。

1. **先定义问题，再选技术。** Redis 是因为 LLOOGG 的 MySQL 撑不住实时统计才诞生的，不是 antirez 先想造数据库再找场景；Vite 是因为 webpack 在大型项目上 dev server 太慢才出现的。技术选型必须挂在真实痛点上，选型文档第一段应该写"要解决什么"，而不是"我们用了什么"。违例信号：方案里出现一堆技术名词，却说不出每个解决了哪个具体问题。
2. **简单性是可维护性的上限。** SQLite 用"数据库就是一个文件"的模型把复杂度压到极致：约 15.6 万行（155.8 KSLOC）核心代码，由约 9.2 万 KSLOC 的测试代码与测试脚本守护（约为核心代码的 590 倍）；Go 砍掉继承、泛型推迟十年，才换来今天碾压级的编译速度和团队上手效率。每加一个抽象、一个配置项、一个依赖，都要问：它带来的复杂度是否小于它消灭的复杂度？如果一个功能"可能以后用得上"，那它现在就不应该存在。
3. **稳定接口 + 内部自由演进。** Linux 的 syscall 就是几十年不变的"合同"，内核内部却每版本都在大改；PostgreSQL 的 SQL 方言是兼容性承诺，存储引擎、索引实现却可以替换。对外接口契约（API、CLI、数据格式、协议）一旦发布就要谨慎变更，内部实现则要敢于重构。把"接口稳定性"和"实现自由"分开管理，是两个不同的决策维度。
4. **用领域语言建模，消灭翻译层。** Terraform 用 HCL（声明式配置语言）让基础设施描述直接可读、可 diff；Ansible 用 YAML 清单让运维意图对非程序员也可理解；TypeScript 用类型把"这个值是什么"从开发者脑子里搬进代码里。配置、规则、状态都该用接近业务的语言表达，而不是逼用户或调用方在"业务概念"和"代码概念"之间来回翻译。
5. **性能是可预测性与低退化，不是炫技。** nginx 用事件驱动模型让"一万并发"成为默认能力而非调优结果；ClickHouse 为分析查询定制列式存储，让"查得快"来自存储模型而非缓存；Redis 的数据结构和内存模型让复杂操作在单线程下依然可预测。性能设计的核心是：让最坏情况可预测、让退化可控、让用户能把性能当作默认值依赖。
6. **测试与可观测性是设计的一部分，不是收尾工作。** SQLite 拥有覆盖每个代码路径的测试套件和专门的"大巴测试"（随机破坏后验证恢复）；Prometheus 把指标采集设计成系统自身的核心能力而非外挂；Kubernetes 的声明式状态让"当前状态 vs 期望状态"的校验成为天然的自检机制。设计阶段就要想清楚：这条路径怎么测？这个组件怎么观测？出了故障怎么定位？
7. **兼容性是长期承诺，破坏性变更要按版本阶梯释放。** Git 的历史对象格式十几年不变是其生态信任的基石；TypeScript 用"JS 超集 + 渐进采用"让旧代码零成本迁移；Rust 用 edition 机制在语言演进时保住编译期兼容。需要破坏性变更时，给出迁移路径、deprecation 窗口、自动化工具，而不是"升级即碎"。
8. **少即是多，砍功能比加功能难得多。** Docker 只做"打包+运行"一件事，却重塑了整个交付链；Svelte 砍掉虚拟 DOM，换来更小的包体和更直接的运行时；Node.js 从"一个高性能 Web 服务器"起步，没有一开始就铺满模块。MVP 的成功标准是"用户愿意用"，不是"功能齐全"。功能蔓延是项目失败的第一大原因。
9. **一切皆可观测：日志、指标、追踪，三者缺一不可。** Grafana 的成功来自"把指标可视化做得比开源里的任何选择都好 10 倍"；Prometheus 的 pull 模型让指标成为服务自身的对等公民。任何系统上线前必须回答：失败时我靠什么定位？瓶颈时我靠什么发现？这个回答不能是"看日志"三个字，必须是具体的指标面板与告警规则。
10. **迭代要快，但契约要慢。** webpack 快速迭代赢得生态，Vite 却靠"用 esbuild 预打包依赖 + 原生 ESM"的架构飞跃实现 dev server 提速 10 倍以上；Godot 低调打磨十余年才开源，靠完整编辑器生态一举站稳。面向成长性任务要快速试错、小步发布；面向用户契约的功能要深思熟虑再推出，一旦推出就要长期维护。

## 任务规模分档（先判定，再裁剪）

进入五阶段工作流前，先按下面**可判定的条件**给任务分档。分档决定阶段产物保留多少、删掉多少——分档不是免责，小任务也必须用心法与最小校验收尾。

| 档位 | 判定条件（满足任一即升档） | 工作流裁剪 |
|---|---|---|
| **S 小改** | 改动 < 200 行；≤ 1 个文件；只改既有代码、不新增模块 | 跳过阶段二正式文档；直接实现 + 必要测试；过一遍终检清单，跑 `scripts/preflight.py` |
| **M 中型** | 改动 200–5000 行；2–20 个文件；新建一个服务/组件/模块；单人可完成 | 完整五阶段；阶段二出精简设计文档（选型表 + 数据流 + 失败模式）；每个里程碑可验收 |
| **L 大型** | 改动 > 5000 行；> 20 个文件；多个模块/子系统/团队协作；需长期演进与上线后维护 | 完整五阶段；阶段二出可评审设计文档；里程碑 + 评审 + 升级路径 + 可观测性全套；终检清单逐项自检并附 `preflight.py` 输出 |

判定依据优先级：**新系统 > 大改动 > 小改动**。新建哪怕只有 100 行的关键组件也按 M 起步（它决定后续所有代码的走向）；给既有项目加一个独立服务按 M；完整新平台/跨团队改造按 L。拿不准时升一档——多读一个模块比漏掉一个阶段安全。

## 标准工作流（五阶段）

这是本技能规定的执行骨架。具体细节按上文任务规模分档裁剪：S 档跳过阶段二的正式产出，直接在实现时应用心法；M/L 档必须完整走，L 档还要补评审与升级路径。

### 阶段一：需求澄清

目标：在写第一行代码前，把"做什么、给谁用、验收标准是什么"钉死。

1. **识别真实问题**：用户说的需求背后是什么痛点？复述并确认，不替用户发明需求。
2. **定义用户与场景**：谁会用它？在什么场景下用？写出一段"用户故事"。
3. **划定范围**：MVP 包含什么、不包含什么。写下"不做清单"，防止蔓延。
4. **明确验收标准**：可量化的完成标准（功能、性能、可用性数字）。没有验收标准的需求等于没有需求。
5. **识别约束**：平台、语言、预算、时间、合规、团队能力——约束是后面的选型边界。

**产出**：一段需求描述（问题/用户/范围/验收/约束），100-500 字。与用户确认后再进入设计。

### 阶段二：架构设计

目标：产出可评审的设计文档，让任何工程师（或 Agent）能照着实现不跑偏。

1. **技术选型绑定痛点**：每一项选型写出"解决哪个问题、代价是什么、备选是什么"，用表格对比。
2. **画数据流与模块边界**：数据从哪来、存在哪、往哪去；模块之间通过什么接口通信。
3. **定义核心数据模型**：实体、关系、主键、索引策略。数据模型错误是返工成本最高的错误。
4. **设计失败模式**：每个模块如果挂了会发生什么？如何降级？如何恢复？（对应心法 6、9）
5. **列出里程碑**：把实现切成可独立验证的里程碑，每个里程碑有明确验收。参考 `06-from-zero-to-ship.md` 的里程碑拆分方法。

**产出**：设计文档（目标、选型表、架构图/文字、数据模型、失败模式、里程碑）。大型任务先出文档再写代码。

### 阶段三：实现

目标：写出可读、可测、可维护的代码，而不是"能跑"的代码。

1. **小步提交**：每个逻辑单元一个提交，提交信息说明"为什么"而非"改了什么"。
2. **接口先行**：先定义模块边界再填实现；让调用方代码先能编译/通过类型检查。
3. **把复杂逻辑拆小**：一个函数只做一件事；超过 50 行的函数考虑拆分（对应心法 2、4）。
4. **错误处理是功能的一部分**：每个可能失败的调用都要有明确的错误路径，不吞异常。
5. **留下可观测钩子**：日志、指标、关键路径计时在实现时同步写入，不后补。
6. **边实现边写测试**：核心逻辑与测试同步编写，而不是全部写完再补。

### 阶段四：验证

目标：用证据证明"它是对的"，而不是"它看起来对"。

1. **单元测试**：覆盖核心算法与边界；用表驱动测试覆盖多组输入输出。
2. **集成测试**：验证模块间契约；数据读写、外部依赖 mock 与真实两种都跑。
3. **端到端（E2E）**：从用户入口到最终结果全链路走通。
4. **性能与并发**：关键路径压测，确认最坏情况在预算内；不做无限优化。
5. **负面测试**：错误的输入、缺失的依赖、中断的流程——系统应当优雅失败。
6. **自问**：我是写测试证明它对，还是写测试为它背书？后者不如不写。

### 阶段五：交付

目标：让用户能无痛使用，并在出问题时能自己定位。

1. **文档与示例**：README 回答"这是什么、怎么装、怎么用、怎么扩展"；附最小可运行示例。
2. **构建与发布**：一键构建、可复现（锁版本、锁依赖）；发布产物带版本号。
3. **升级路径**：老用户如何升级？配置/数据是否需要迁移？给出迁移工具或说明。
4. **可观测性验收**：上线后靠什么监控？失败怎么定位？（对应心法 9）
5. **反馈闭环**：留下反馈入口，记录已知问题与路线图；大系统附 CHANGELOG。

## 终检清单

交付前逐项自检（可对照 `06-from-zero-to-ship.md` 的完整案例自评）：

- [ ] 需求是否有明确验收标准？是否与真实问题对齐，而不是炫技？
- [ ] 技术选型是否每项都绑定了具体痛点？有没有为了"新潮"引入的组件？
- [ ] 数据模型是否稳定？有没有需要迁移才能改的硬编码？
- [ ] 错误路径是否全部处理？系统能不能优雅失败而非崩溃？
- [ ] 关键路径是否可观测（日志/指标/追踪）？
- [ ] 测试是否覆盖核心逻辑与边界？性能最坏情况是否在预算内？
- [ ] 接口契约是否明确且稳定？破坏性变更是否给了迁移路径？
- [ ] 是否保留了"不做清单"里的功能扩散迹象？（心法 8）
- [ ] 交付物是否有文档、示例、构建与发布说明？
- [ ] 整个链路有没有证据支撑（不是"看起来可行"，而是验证过）？
- [ ] 若交付项目（非单文件脚本）：已在项目根目录运行 `python scripts/preflight.py .`，无 FAIL 项？（README/CI/锁文件/测试/错误路径可观测/占位符六项为可执行子集，其余项人工自检）
