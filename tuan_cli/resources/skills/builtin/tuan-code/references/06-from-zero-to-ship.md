# 模块六 · 从零到落地完整案例：Lore

**模块定位**：本文件是一个**可套用的完整工程实录**。它展示一个新颖软件——**Lore：本地优先的 AI 编程助手**——如何从一纸需求出发，经过设计、实现、测试、部署、上线，最终成为一个可下载、可升级、可迭代的开源产品。读完本文件，你应该能照着它把任何"从零到一"的软件项目切成里程碑、排兵布阵、逐关验收。

> **重要声明：Lore 是虚构示例，不是真实项目。** 文中一切精确数字——10 万行/30 秒的索引性能、payload < 20k token、6 周单人周期、20 位内测用户等——均为**示例值，非任何真实项目的实测数据**。迁移到你的项目时，请按实际情况重新标定，不要把示例值当行业基准。

案例中每个环节都标注了**对应的模块/法则出处**，方便回查：例如"[01-SQLite]"指 `01-systems-foundations.md` 中 SQLite 深拆的教训。

## 产品一句话

**Lore 是一个跑在你自己的机器上、能读懂你的代码库、所有动作都有审计记录的开源 AI 编程助手。**

**新颖点**（2026 年语境）：当主流 AI 编程助手都以"云端优先"为主时，Lore 选择 **本地优先**：会话数据、项目索引、审计日志全部留在本机；模型可选本地（Ollama）或云端 API；每一次文件写入、命令执行都有不可篡改的审计轨迹。它把"AI 帮我写代码"这件事，从"黑箱外包"变成"可审计、可离线、密钥不出机"的工程实践。

## 阶段一：需求（2 天）

### 1.1 识别真实问题

用户（隐私敏感的个人开发者/小团队）对现有 AI 编程助手的核心不满：
1. **代码上云**：仓库内容、会话记录被发送到厂商服务器，涉密项目不敢用。
2. **密钥与权限不透明**：助手能读哪些文件、跑什么命令，用户说不清、查不到。
3. **不可离线**：网络一断，助手变废铁；本地模型想接也接不上。
4. **动作不可审计**：AI 改了哪个文件、跑了哪个命令，事后无法回查（出了事故说不清责任）。

> 对应法则：[03-核心法则 1]（先定义数据流/痛点再定义系统）、[01-核心法则 7]（可观测性是出厂配置）。

### 1.2 用户与场景

- **用户故事 A（个人）**：我是独立开发者，项目里有客户密钥文件。我希望助手能读懂并修改代码，但绝不能把 repo 内容发到云上，所有文件写操作我要能事后查。
- **用户故事 B（小团队）**：我们团队用私有 GitLab，安全合规要求代码不出内网。我们希望 AI 助手接内网 Ollama 跑本地模型，同时每个改动能 trace 到是哪条指令触发的。

### 1.3 MVP 范围（cut 狠一点）

**包含**：
- CLI 交互：启动会话、多轮对话、`/exit` `/skills` 等命令。
- 双模 LLM：本地 Ollama + OpenAI 兼容 API（密钥只存本机配置文件，绝不上传）。
- 项目感知：扫描仓库生成轻量索引，检索相关文件注入上下文（不把全仓库塞进去）。
- 工具沙箱：受控地读写文件、执行测试/构建命令；每次动作写审计日志。
- 审计日志：本地 SQLite，记录"谁（会话）在何时请求了什么、助手读了什么、写了什么、跑了什么命令"。

**不做清单**（明确拒绝，防止蔓延，[心法 8]）：
- ❌ 不做 GUI/IDE 插件（v2 的 Electron 壳）
- ❌ 不做云端同步/多设备（v2）
- ❌ 不做团队协作/权限管理（v2）
- ❌ 不做模型训练/微调
- ❌ 不做自动提交 git（v1.1 再讨论，安全敏感）

### 1.4 验收标准（可量化）

| # | 验收项 | 标准 |
|---|---|---|
| 1 | 离线闭环 | 断网 + 本地 Ollama 下，能完成"理解项目→改一个文件→跑测试"的完整流程 |
| 2 | 密钥安全 | 启动后 `lore keys` 显示"密钥已配置于 ~/.config/lore/config.toml，未外发"；代码中零硬编码 |
| 3 | 审计完整 | 每 100 次工具调用，审计日志查得到 100 条，含时间/指令/文件路径/命令 |
| 4 | 索引性能 | 10 万行仓库（约 2000 文件）建索引 < 30 秒，检索 < 500ms（示例值） |
| 5 | 沙箱安全 | 目录穿越/符号链接逃逸测试全部拒绝（见测试阶段） |
| 6 | 文档 | README + 快速开始 + 技能开发文档，示例可跑 |

### 1.5 约束

- 语言：Rust（见选型，若团队无人会 Rust 则降级 Go，但演示场景按 Rust 走）。
- 平台：Linux/macOS 优先（Windows 放 v1.1）。
- 时间：6 周（单人全职，示例值），每周一个里程碑。
- 合规：密钥不进 git、审计日志不对外、远端 API 仅发送"检索后的相关片段"而非全仓库。

**阶段一验收**：产出需求文档（上文）+ 与用户确认。确认后才允许进入设计。

## 阶段二：设计（3 天）

### 2.1 架构总览（一个进程，四条管道）

```
用户 (CLI/TUI)
   │
   ▼
┌─────────────────────────┐
│ 会话引擎 SessionEngine   │  ← 状态机：管理对话、工具循环、技能切换
└─────────┬───────────────┘
          │
   ┌──────┼──────────────┬─────────────┐
   ▼      ▼              ▼             ▼
上下文管道  工具沙箱      LLM 网关    技能加载器
Context     Toolbox      LLMGateway   SkillLoader
   │        │  ┌───────┐ │            │
   ▼        ▼  │ 审计   │ ▼            ▼
本地索引   FS/Sh  │日志   │ Ollama│  skills/ 目录
(repo index) │(SQLite) │ /API  │  (markdown 技能)
             └────────┘        └───────┘
```

**设计要点**：
- 单二进制（Rust），全部逻辑一个进程内，默认行为"简单到无配置可跑"（[01-SQLite] 极简模型）。
- 工具沙箱是唯一会碰文件系统/进程的模块，其他模块不得直接执行外部副作用 → 审计自然收敛到一处（[01-核心法则 7]、[02-Kubernetes] 接口收敛）。
- LLM 网关是唯一网络出口，且只发送"检索后的相关片段"（[03-Kafka] 总线收口）。

### 2.2 技术选型表（每项绑定痛点）

| 项 | 选择 | 解决哪个问题 | 代价 | 备选 |
|---|---|---|---|---|
| 语言 | Rust | 单文件分发、低内存、工具链统一（cargo） | 上手曲线 | Go（团队熟悉可换，架构不变） |
| 存储 | SQLite（rusqlite） | 零配置本地化，审计与会话永不丢 | 单写者（本项目够用） | sled/redb |
| 配置 | TOML 单文件 `~/.config/lore/config.toml` | 人类可读、可 diff、可审计 | 无 schema 校验工具 | YAML |
| CLI 框架 | clap（derive） | 参数解析规范、help 自动生成 | 无 | 手写 parse |
| 项目索引 | tree-sitter（符号）+ ripgrep（全文） | 精准定位符号、全文检索快 | 依赖 tree-sitter 语法文件 | 纯 ripgrep（v0.9 前够用） |
| LLM 网关 | Ollama HTTP + OpenAI 兼容 API 双后端 | 本地/云端双模 | 两套参数映射 | 只接 OpenAI |
| 审计 | SQLite 表 + WAL | 原子写入、崩溃安全（[01-SQLite/PostgreSQL]） | WAL 文件需备份策略 | JSONL 文件（v1.1 迁移） |
| 遥测 | 事件文件 + 可关闭开关 | 匿名改进（不发代码内容） | 隐私合规需认真做 | 不做（但会盲飞） |
| CI/CD | GitHub Actions matrix | 三平台产物 + 自动发布 | Actions 分钟数 | 本地脚本 |

> 对应法则：[心法 1]（选型绑定痛点）、[心法 2]（简单性）。

### 2.3 核心数据模型

```sql
-- 会话
sessions(id TEXT PK, created_at INT, cwd TEXT, model TEXT, skill_id TEXT NULL);
-- 消息（含助手思维链与最终回复）
messages(id INTEGER PK, session_id TEXT FK, role TEXT, content TEXT, created_at INT);
-- 工具调用（写审计所需字段）
tool_calls(id INTEGER PK, session_id TEXT FK, message_id INT FK,
           tool TEXT, input_json TEXT, output_json TEXT, ok INT, created_at INT);
-- 审计事件（独立于业务，只增不改）
audit_events(id INTEGER PK, session_id TEXT FK, ts INT, actor TEXT,
             action TEXT, target TEXT, details TEXT);
-- 键值配置（密钥标记等）
kv_store(k TEXT PK, v TEXT);
-- 索引表
index_entries(id INTEGER PK, path TEXT, symbol TEXT, kind TEXT, line INT);
```

设计决策：**审计日志独立成表、只增不改**——借鉴 [01-Git] 不可变对象，保证"事后可追溯"这一承诺在数据结构上就成立；**WAL 模式**借用 [01-SQLite] 崩溃安全教训。

### 2.4 失败模式（每个都要写"会怎样 + 怎么办"）

| 失败 | 表现 | 降级/恢复 |
|---|---|---|
| LLM 不可达 | 网关超时 | 重试 2 次 → 明确报错"模型不可达"；本地 Ollama 未开时提示 `ollama serve` |
| 远端 API 限流 | 429 | 指数退避重试；把"排队中"写进状态行 |
| 写文件被拒 | 沙箱拦截 | 输出"操作被安全策略拒绝：路径超出工作区" |
| 索引损坏 | 检索异常 | `lore index rebuild` 重建；索引与源文件分离可随时重算（[02-Terraform] 状态可重建） |
| 命令超时 | 工具循环挂起 | 默认 60s 超时 + 可配；超时输出部分 stdout/stderr |
| 审计写失败 | 存储异常 | **阻断后续工具调用**（安全红线：宁停勿漏记，[心法 6]） |

### 2.5 里程碑（6 周，每周一个可验收里程碑）

| 周 | 里程碑 | 可验收标准 |
|---|---|---|
| M0 | 骨架 | `lore --version` 可跑；配置读取；日志框架；CI 空跑通过 |
| M1 | 会话闭环 | 本地模式能多轮对话；`/exit` 正常；消息落 SQLite |
| M2 | 工具沙箱+审计 | 能读文件/写文件/跑命令；100% 进审计；路径穿越拦截 |
| M3 | 项目感知 | 建索引、检索相关片段注入上下文；10 万行 30s 验收过 |
| M4 | 技能系统 | `lore skills` 列出/加载技能；技能文件为 markdown（与本技能"总纲 + references/ 按需加载"的结构一致） |
| M5 | 测试与打磨 | 测试矩阵全绿；README/快速开始/文档；错误信息友好化 |
| M6 | 打包发布 | 三平台产物 + 签名 + 语义化版本 + Homebrew tap 安装 `brew install lore` |

> 里程碑拆分方法可直接复制到任何项目：**每个里程碑都是"用户能感知的一个能力台阶"，且有数字验收**。

**阶段二验收**：产出一份设计文档（上述 2.1-2.5）。大型项目的设计文档应让另一位工程师读完能独立实现，本案例即以此为标准。

## 阶段三：实现（M0→M6）

### 目录结构（M0 就定好，后续不动大框架）

```
lore/
├── Cargo.toml
├── src/
│   ├── main.rs            # 入口：参数 → App 装配
│   ├── config.rs          # TOML 配置解析（密钥标记、模型设置）
│   ├── session.rs         # 会话状态机（对话/工具循环/技能切换）
│   ├── context.rs         # 上下文管道（索引检索 + 片段组装）
│   ├── index.rs           # tree-sitter/ripgrep 索引
│   ├── engine/
│   │   ├── llm_gateway.rs # Ollama + OpenAI 兼容双后端
│   │   └── prompt.rs      # 系统提示模板（技能注入点）
│   ├── toolbox/
│   │   ├── fs.rs          # 读/写文件（路径校验核心）
│   │   ├── exec.rs        # 命令执行（超时/白名单）
│   │   └── audit.rs       # 审计写入（阻断语义）
│   ├── skills.rs          # 技能发现/加载/渲染
│   └── store.rs           # SQLite（schema 迁移）
├── skills/                # 内置技能（markdown）
├── tests/                 # 集成/E2E
└── docs/
```

### 关键实现决策（边写边记录的 ADR）

**ADR-001 路径校验：拒绝而非转义**（M2）
- 背景：沙箱要防止目录穿越（`../../etc/passwd`）与符号链接逃逸。
- 决策：每次写操作前 canonicalize 目标路径，断言其前缀为工作区根；不通过即拒绝并审计。不尝试"智能转义"——拒绝对应 [心法 6] 的可预期性。
- 结果：测试阶段"穿越/软链逃逸"用例全部拒绝。

**ADR-002 审计写入失败即阻断**（M2）
- 背景：审计是被承诺的一等能力（需求验收 #3）。
- 决策：工具执行后先写 audit_events，写失败则工具结果标记 `ok=false` 且不继续下一步。宁可少完成一个任务，不可产生"无记录的副作用"。
- 结果：验收 #3 天然满足；出故障时用户看到明确错误而非静默丢记录。

**ADR-003 上下文窗口：先检索后截断**（M3）
- 背景：直接把全仓库塞给 LLM 不可行（token 爆炸、噪声大）。
- 决策：用户指令 → 用关键词/符号检索 top-k 片段（按符号、import 关系加权）→ 组装到系统提示的"相关代码"区；超过模型窗口时按行号区间截断并注明"已省略 N 行，请用 /read 查看"。上下文管道只在 `context.rs` 内实现，LLM 网关不关心来源（[02-Prometheus] 标签维度思想：上下文=输入信号，隔离变化）。
- 结果：10 万行仓库请求 payload 恒 < 20k token（示例值，非实测），可离线跑小模型。

**ADR-004 技能 = 普通 markdown 目录**（M4）
- 背景：要对齐"按任务加载方法论"（本技能自身的模式）。
- 决策：`skills/<name>/SKILL.md`（frontmatter: name/description）+ 可选 references/。会话引擎在发起请求前，把命中的技能正文渲染进系统提示；技能之间不合并、不自动跨技能（避免冲突）。
- 结果：技能生态零代码接入，与本技能"总纲（SKILL.md）+ references/ 深度模块按需加载"的结构一致，迁移顺畅。

**ADR-005 密钥不进任何文件的历史**（M1 起坚持）
- 背景：远端 API key 是最高敏感物。
- 决策：密钥只写 `~/.config/lore/config.toml`（权限 600）；`lore keys` 只显示"已配置/未配置"，不回显明文；gitignore 全局排除 config.toml；进程内不存日志。审计记录"何时配置过 key"，不记录 key 本身。
- 结果：验收 #2 通过；README 向用户说明"密钥只在你机器上"。

**ADR-006 会话循环的单线程结构**（M1）
- 背景：避免并发复杂化（[01-Redis] 单线程减法）。
- 决策：v1 全部单线程：读输入 → 组装上下文 → 调 LLM → 循环解析工具调用 → 执行 → 再组装。并发留给未来（工具执行本身是阻塞的，用户可 Ctrl-C 中断）。
- 结果：日志与审计顺序天然一致，调试成本极低。

### 每个里程碑的"完成动作"

M0 完成：`cargo run -- --version` 输出 `lore 0.1.0`；CI 上 `cargo lint && cargo test` 空跑绿。
M1 完成：三平台手动跑通对话闭环（验收 #1 的对话部分）。
M2 完成：写审计脚本模拟 100 次调用，查 SQLite 断言 100 条（完成条件写进测试，[01-SQLite] 测试驱动）。
M3 完成：benchmark 脚本对 10 万行夹具仓库计时（验收 #4）。
M4 完成：示例技能"code-review"能让助手按步骤审查代码。
M5 完成：测试矩阵全绿 + 文档可跑（README 示例逐字执行一遍）。
M6 完成：`cargo build --release` 三平台 artifact + GitHub Release + tap。

## 阶段四：测试（贯穿，M5 集中冲刺）

### 测试矩阵（全部进 CI）

| 层 | 用例 | 工具 |
|---|---|---|
| 单元 | 路径校验（穿越/软链/相对路径）、会话状态机、prompt 模板渲染、配置解析边界 | cargo test |
| 集成 | 对 mock Ollama 网关的会话闭环、工具沙箱读写真实临时目录、审计写入 SQLite | cargo test + fixtures |
| E2E | 模拟"改一个函数 → 跑测试 → 断言通过"全流程（README 示例） | tests/e2e.rs |
| 安全 | 目录穿越 100+ 用例、符号链接逃逸、命令注入（`; rm -rf` 等）、密钥不回显 | security.rs 专项 |
| 性能 | 10 万行索引计时、检索计时、首 token 延迟（本地模型） | bench 脚本 |
| 故障 | LLM 超时重试、限流退避、审计写失败阻断、索引损坏重建 | fault.rs |

### 关于"测试为谁而写"

- 守护验收标准：验收 #3（审计完整）用"100 次调用 → 断言 100 条"的集成测试直接固化，防止未来重构破坏承诺。
- 守护安全红线：路径校验测试用表驱动海量恶意路径（`../`、`../../`、绝对路径、软链接），比人工 review 可靠（[01-SQLite] 大巴测试精神）。
- 不为测试而测试：UI 文案、TUI 布局不做单测，交给 E2E 快照。

## 阶段五：部署（M6）

### 5.1 构建与发布

- 发布流程（GitHub Actions）：
  1. tag `v0.x.y`（语义化版本，[心法 7] 版本阶梯）
  2. matrix: ubuntu-latest / macos-latest（+ windows 若 v1.1）
  3. `cargo build --release` → 压缩 artifact → 附 SHA256 摘要（审计/供应链自证）
  4. 自动生成 CHANGELOG（conventional commits）、GitHub Release 说明
- 安装渠道：
  - Homebrew tap：`brew install lore-lang/tap/lore`（致敬 [05-Homebrew] 配方即代码）
  - 直接下载：Release artifact（单文件二进制，含内置 skills 目录）
- 签名：macOS 用开发者证书公证（Gatekeeper），Linux 提供校验和（信任链自证）。

### 5.2 升级路径（[心法 3] 兼容承诺）

- 数据 schema 用显式 migration（SQLite `PRAGMA user_version`），升级自动迁移并在日志写明"已从 v1 升到 v2"。
- 配置向后兼容：新字段有默认值，旧配置可继续运行；破坏性配置变更走 deprecation 警告一个版本周期。
- 技能格式一旦 M4 定型，对外就进入兼容承诺（社区技能依赖它）。

## 阶段六：上线（M6 之后持续）

### 6.1 灰度与反馈闭环

- **先遣队（2 周）**：邀请 20 位隐私敏感开发者内测，重点收集：初次安装体验、审计日志可读性、本地模型下"能用"的模型清单。用 GitHub Discussions + 内测问卷。
- **Public Beta（4 周）**：README 上线、Hacker News/Reddit 发布；使用 `opt-in` 匿名遥测（事件仅含"用了哪个命令、哪个模型、是否成功"，不含代码内容、路径、密钥）。
- 反馈渠道：GitHub Issues 模板（bug 报告自动附 diagnostics 命令输出）、Discussions 路线图投票。

### 6.2 可观测性（借鉴 [02-Prometheus/Grafana]）

自托管端不引入服务器监控，但内置：
- `lore diag` 一条命令输出版本、配置路径（不回显密钥）、索引状态、最近审计条数。
- 崩溃自动写 `~/.local/state/lore/crash-*.log`（含版本号与栈），用户可一键附到 issue。
- 兼容 OpenTelemetry trace 导出（可选，供自建监控的用户接入）。

### 6.3 迭代节奏

- 每 2 周一个小版本（bugfix/小特性），每季度一个大版本（数据/接口变更）。
- 每版发布前回放一遍"验收标准表"，防慢性漂移。
- 路线图公开，重大方向（如 GUI、多设备同步）在 RFC 讨论后进入 backlog。

## 可复用模板（复制即用）

**需求模板**
```
产品一句话：____（<30 字，含受众+价值）
痛点 1-4：____（每条都要有反例，证明真实）
MVP 包含：____（按用户故事列）
不做清单：____（每条写明理由）
验收标准：编号表（可量化）
约束：平台/时间/合规/团队
```

**选型表模板**
```
| 项 | 选择 | 解决哪个问题 | 代价 | 备选 |
每行必须能回答"为什么是它"——答不上来就不选。
```

**里程碑模板**
```
M0 骨架：____（版本号可跑）
M1 最小闭环：____（用户能感知的第一个能力台阶）
M2 核心机制：____（安全/数据/并发等关键路径）
M3 体验补齐：____（性能/可用性）
M4 扩展点：____（技能/插件/协议）
M5 打磨：____（测试矩阵/文档）
M6 发布：____（多平台产物/安装渠道/升级路径）
```

**终检问题（交付前）**
1. 验收标准表是否有任何一项没有数字证据？
2. 最近一次完整跑测试矩阵是什么时候？
3. 出故障时，用户第一条诊断命令是什么（`diag`/`--version`/日志路径）？
4. 有哪些"偷偷超出不做清单"的功能？（有就砍）
5. 老用户升级是否会无声碎掉？（跑一遍迁移测试）

## 一句话提醒

Lore 案例证明：**"从零到落地"不是一次大爆炸，而是把"需求→设计→实现→测试→部署→上线"切成 6-8 个可验收台阶，每一阶都用数字验收 + 法则对照 + 安全红线兜底**。照着这个模板推进，任何新软件都能在两三个月内从想法变成可下载、可升级、可迭代的真实产品。
